# 束：検索パリティ 項目4「型付き再射要求」実装（PC CC 席向け・発射は再ゲート通過後）

状態：**準備済み・未発射**。検索パリティ本体（項目1/2/3/5）の再ゲート通過が確定した時点で、ハヤトがこの束をそのまま発射する。前提として本体ブランチ `feat/search-parity` が main にマージ済みであること（本束はその上に積む）。

## 目的
MCP の型付き op を1つ追加する。引数は **opt-in 済みパイプライン ID のみ**（自由文なし）。S5（executor recovery）のアプリ側単一再射経路に載せ、呼び出し側が寄与するのは「どの承認済みパイプラインを、いつ」だけにする。背景と評決は `~/workspace/research/search-parity/fact-sheet.md`（Fable 評決の節）と S5 の事実シート `~/workspace/research/executor-recovery/fact-sheet.md`。

## 実装範囲
1. 新しい MCP typed op（名称は既存の命名に合わせる。例：`request_pipeline_refire`）：
   - 引数は pipelineId のみ。厳格スキーマ（追加フィールドは拒否）。
   - 対象は Web 検索 opt-in 済みパイプラインに限る（opt-in の同意ハッシュ検証を再利用）。
   - 受理条件：当日のそのパイプラインのランが、回復可能な理由で held / failed のときだけ。それ以外は理由コードつきで拒否。
   - 冪等（同じ当日の再射要求の重複は1回に畳む）。1日上限 1〜2回（パイプライン単位）。
   - STOP-ALL が有効な間は拒否（理由コード halted）。
   - 再射の実行は S5 のアプリ側経路（2時間窓・exactly once・未配信のみ）の規則に従う。新規の実行経路を作らない。
2. 監査：要求・受理・拒否（理由コード）を既存の監査に記録。
3. 永続性：再射要求はアプリ kill・更新・再起動をまたいで保持されること（S5 の再射が次回起動スイープで拾える形）。
4. 常時許可：この op は typed op として always-allow の対象にできること（service_control と同じ登録方式）。ただし再射の受理条件チェックは常時許可でも省略しない。

## 受け入れ条件
- 自由文や追加引数を渡す呼び出しが拒否される（テスト）。
- opt-in されていないパイプラインへの要求が拒否される。
- 当日に回復可能な held/failed が無い場合は理由コードつきで拒否される。
- 重複要求が二重再射にならない。1日上限を超えた要求が拒否される。
- STOP-ALL 中は拒否される。
- アプリ再起動をまたいだ要求が、次回起動の調整で再射として実行される（S5 の既存スイープとの接続テスト）。
- executor 本体の挙動（項目1/2/3/5）には触らない。触る場合は理由を返却に明記。
