## Addendum 3（2026-11-25 18:2x、ハヤト記入：キャップの執行可能な形への明確化）
ゲート3回目の所見1を受けて、37行目の「1ランあたりのクエリ数・長さに上限、全クエリ監査」の執行形を、実測されたプラットフォーム制約に基づいて明確化する（シートの要求が物理的に執行不可能な形だったため、意図を保ったまま執行可能な形に直す）。
- 制約（実測）：hosted 検索のクエリは `item/completed` までクライアントに見えない。開始時点での切り詰め・事前の長さ検査はできない。
- 執行形（適合の定義）：(i) 完了済み使用量＋実行中アイテムの予約分が上限を超える状態では、新しい検索を開始しない。(ii) 飛行中の超過は予約分（1アイテム=1バッチ分）の範囲に bounded される。(iii) **完了したクエリはすべて計数・監査される**。停止判断の後で完了するアイテムも同様で、最終件数の確定は「未決アイテムの決着を待つ」か「決着しない場合は推定として executor に全消費（fail closed）と読ませる」のどちらかとし、過小な確定値を黙って書くことは禁止。(iv) 長さ超過のクエリは完了時に検出して計数・監査し、その場でターンを止め、ランは held に着地する。
- Fable 条件の意図（露出の bounded 化＋全監査＋fail closed）はこの形で満たす。事前の hard cap が物理的に可能な経路（自前の検索実行など）に移る場合は、その時点で本 addendum を見直す。
